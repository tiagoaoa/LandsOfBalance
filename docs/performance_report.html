Critical Rendering Pipeline

These are the core settings that control how every single pixel on screen is computed. They have the largest impact on both desktop and mobile performance.

SettingCurrent ValueDesktop ImpactMobile Impact
Rendering Method Forward+ Good Very Heavy
Shadow Atlas Size 8192 × 8192 Heavy Extremely Heavy
MSAA (3D) 2x Moderate Heavy
Anisotropic Filtering Level 4 Low Moderate
Moon Shadow Cascades 2 splits Low Moderate
Rendering Method (Forward+): This determines the entire rendering architecture. Forward+ is Godot's most feature-rich renderer — it supports SDFGI, volumetric fog, advanced lighting, and more. However, it performs multiple rendering passes per light and per object, making it extremely expensive on mobile GPUs. The Mobile renderer is a stripped-down forward renderer optimized for phones. GL Compatibility uses OpenGL ES 3.0 instead of Vulkan, supporting the widest range of devices but with fewer features.
Shadow Atlas: When lights cast shadows, the engine renders the scene from the light's perspective into a shadow map — a depth texture. The shadow atlas is the large texture that holds all these shadow maps. At 8192×8192 pixels, that's a 67-million-pixel texture that must be rendered and sampled every frame. On a phone, reducing this to 2048×2048 cuts the workload by 16×.
MSAA (Multi-Sample Anti-Aliasing): Jagged edges appear where 3D geometry meets the background. MSAA smooths these by computing each pixel multiple times at slightly different positions. 2x MSAA means every pixel is sampled twice, roughly doubling the fragment shader work. On mobile GPUs with limited fill-rate, this is a significant cost for a mostly cosmetic benefit.
Anisotropic Filtering: When a textured surface is viewed at a steep angle (like a road stretching into the distance), textures become blurry. Anisotropic filtering takes extra texture samples to keep them sharp. Level 4 means up to 4 extra samples per pixel. On mobile, level 1-2 is usually sufficient.
Shadow Cascades: For directional lights (sun/moon), the scene is divided into distance ranges called cascades. Each cascade gets its own shadow map rendering pass. 2 splits means 2 separate shadow maps rendered each frame. Reducing to 1 split halves the shadow rendering work, at the cost of lower shadow quality at distance.

High 3D Models & Meshes

Every 3D model consists of triangles (polygons) that the GPU must process. Larger files generally mean more triangles, more vertex data, and more VRAM consumed.

AssetFile SizeNotes
medieval_fortress_kit.glb53 MBCastle builder asset — largest single mesh
Archer.fbx + Archer_Spell.fbx26 + 25 MBPlayer character with animations baked in
dragon.glb15 MBDragon enemy with full skeleton
bobba_character.fbx14 MBBobba enemy model
realistic_grass.glb3.8 MBSingle grass clump, instanced via MultiMesh
village_of_eights.fbx1 MBVillage buildings
mountain.obj315 KBMountain mesh, instanced 3 times
Why file size matters: A 53 MB GLB file like the fortress kit contains tens of thousands of triangles. The GPU must transform every vertex and rasterize every triangle each frame. On a phone GPU, a high-poly model can single-handedly tank the framerate. Additionally, large meshes consume VRAM (video memory) — phones typically have 2-6 GB shared between the OS and apps.
FBX animation data: The Archer files are 25-26 MB each partly because animation keyframes are baked into the file. Each animation clip stores bone transforms for every frame, inflating the file size. These are loaded into RAM even if the animation isn't playing.

High Textures

Textures are images wrapped onto 3D surfaces. They consume GPU memory and bandwidth — the GPU must read from them for every visible pixel.

Texture GroupResolutionCountSize (approx)
Bobba character skins2048 × 20484 files~22 MB
Medieval fortress kit1024 × 102454 files~60 MB
Ground material maps (Color, Normal, AO, Roughness)1024 × 10245 files~12 MB
Dragon textures1024 × 10242 files~3.3 MB
HUD / UI iconsSmall~10 files~0.5 MB
Texture memory vs. file size: A 1024×1024 PNG may be 2 MB on disk, but in GPU memory it's stored uncompressed (or in a GPU-compressed format like ASTC/BC). A single RGBA 1024×1024 texture uses 4 MB of VRAM. A 2048×2048 texture uses 16 MB. With 168 textures, total VRAM usage can easily exceed 500 MB.
Normal maps, AO maps, Roughness maps: Modern PBR (Physically Based Rendering) materials use multiple texture maps per surface — color, normal (surface detail), ambient occlusion (shadow detail), and roughness. Each is a separate texture the GPU must sample. The ground alone uses 5 texture lookups per pixel.

High Vegetation (Grass Systems)

Grass is rendered using MultiMesh — a technique where a single mesh is drawn thousands of times with different positions/rotations in a single draw call. Efficient, but still expensive at high counts.

MultiMesh instancing: Instead of creating 666 separate grass nodes (which would mean 666 draw calls), MultiMesh batches them into a single GPU draw call. This is the most efficient way to render repeated objects. However, each instance still adds vertices and fragments the GPU must process.
Interactive grass mode: The SimpleGrassTextured plugin has an "interactive" mode where grass bends when the player walks through it. This works by updating a height map texture every frame and passing it to the grass shader. This means: (1) CPU work to track player position, (2) texture upload to GPU every frame, (3) extra shader complexity per grass blade. Disabling this is a easy performance win.

Medium Particle Emitters

GPU particles are small billboards simulated and rendered by the GPU. Each particle has a position, velocity, color, and size updated per frame.

SourceParticles

Fire effects (various)80 each
Sparks, trails, smoke20-60 each
Peak total: ~600-800
GPU particles (GPUParticles3D): Each particle is a small quad (two triangles) that always faces the camera (billboard). The GPU updates their physics (gravity, velocity, color fade) via a compute shader, then renders them with transparency blending. Transparent objects are expensive because they can't use the depth buffer for early rejection — every particle behind another particle must still be rendered.

Medium Dynamic Lights

Each light source forces additional rendering work. In Forward+, lights are clustered, but each one still adds shader complexity.

Dragon mouth (fill)OmniLight3DAlways
Spell effectsOmniLight3DDuring combat
Arrow trailsOmniLight3DWhen shooting

OmniLight3D: A point light that emits in all directions (like a lightbulb). If shadow-casting is enabled, the engine must render the scene 6 times (one for each face of a cube map) to create the shadow. The dragon's mouth light with shadows enabled is rendering 6 extra passes per frame.
DirectionalLight3D: A light with parallel rays (like the sun or moon). Shadow maps for directional lights use cascaded shadow maps — the scene is rendered multiple times at different distance ranges. With 2 cascades, that's 2 extra full-scene renders per frame.

High CSG Nodes

CSG (Constructive Solid Geometry) builds meshes at runtime by combining primitive shapes. This is great for prototyping but expensive in production.

NodePurpose
MainGround1070 × 1145 unit ground plane
RiverBed, RiverBed2River channel geometry
RiverWater, RiverWater2Water surface planes
TheLongRoadMain road surface
TradeRoadSide road surface
NorthRoadNorthern road
Total: 8 CSG nodes
Why CSG is slow: Every time the scene loads, each CSGBox3D must compute its final mesh by running a boolean geometry algorithm on the CPU. This generates vertices, normals, UVs, and collision shapes from scratch. A static MeshInstance3D loads pre-computed data directly — no computation needed. Baking CSG to static meshes is a one-time fix that eliminates this startup cost and slightly improves per-frame rendering by using optimized mesh data.

Medium Skeletal Animation

Skeletal animation deforms meshes by transforming bones. More bones and more animation tracks mean more CPU work per frame.

AnimationTrack CountDuration

Bobba animationsStandardVarious
Animation tracks: Each track interpolates one property (rotation, position, scale) of one bone, every frame. With 50+ tracks running simultaneously on the dragon, the CPU must compute 50 quaternion interpolations per frame, then propagate transforms down the bone hierarchy to deform the mesh. This is manageable on desktop CPUs but can be significant on mobile ARM processors.

Medium Per-frame Script Execution

Scripts with _process() or _physics_process() run every frame (60 times per second). Each one consumes CPU time.

FunctionScript CountExamples
_process(delta) 17 scripts UI updates, camera, grass plugin, join screen, lighting
_physics_process(delta) 10 scripts Player movement, dragon AI, bobba AI, arrows, remote players
Total: 27 scripts × 60 FPS = 1,620 function calls/second
_process() vs _physics_process(): _process() runs every rendered frame (variable rate). _physics_process() runs at a fixed rate (default 60 Hz) for deterministic physics. Both are executed by Godot's scripting engine (GDScript), which is interpreted and significantly slower than compiled C++ code. Each function call has overhead for the virtual machine dispatch.
27 scripts is moderate for a game of this complexity. The concern is whether any individual script is doing expensive work (e.g., the SimpleGrassTextured plugin iterating through all 481 instances every frame).

Optimization Recommendations (by expected impact)

Ordered from highest to lowest expected framerate improvement. Items marked with a phone icon are mobile-specific.

1
Switch mobile renderer to mobile or gl_compatibility
Use OS.has_feature("mobile") to detect at runtime, or set the project default. This alone can double the framerate on phones by eliminating Forward+ overhead (clustered lighting, advanced material features).
2
Reduce shadow atlas to 2048 on mobile, 4096 on desktop
In Project Settings → Rendering → Lights and Shadows. The current 8192 is overkill even for desktop. This reduces shadow rendering work by 4-16×.
3
Disable MSAA on mobile
Set msaa_3d = 0 for mobile builds. Use FXAA (a cheap post-process alternative) if edge smoothing is needed.
4
Disable or reduce grass on mobile
Hide the 3 GrassMultiMesh nodes and SimpleGrassTextured on mobile. Keep only a reduced RealisticGrass (200-300 instances). This removes ~2,500 mesh instances and the interactive grass per-frame update.
5
Cap dynamic lights on mobile
Disable shadow on the dragon's OmniLight3D (saves 6 cube-face renders per frame). Limit total OmniLights to 2-3 on mobile.
6
Reduce particle counts by 50% on mobile
Halve all .amount values when OS.has_feature("mobile"). Transparent particles are disproportionately expensive on mobile GPUs due to fill-rate limitations.
7
Bake CSG nodes to static meshes
Export the 8 CSGBox3D nodes as MeshInstance3D + CollisionShape3D. Eliminates runtime boolean geometry computation and produces more GPU-friendly mesh data. One-time manual step in the editor.
8
Downscale textures for mobile export
In the Import dock, set max texture size to 1024 for mobile. This reduces VRAM usage by 4× for the 2048×2048 Bobba textures with minimal visual difference on small phone screens.
9
Reduce dragon animation tracks on mobile
Use a simplified wing animation with ~15 tracks instead of 50+ on mobile. The whip effect and body physics response are subtle details invisible on a small screen.
10
Reduce shadow atlas for desktop too
Lower from 8192 to 4096 on desktop. Quality difference is barely noticeable but frees significant GPU bandwidth and VRAM.

Glossary of Rendering Terms

TermDefinition
Draw CallA single command sent from the CPU to the GPU saying "render this mesh with this material." Each draw call has CPU overhead. Fewer draw calls = better performance. MultiMesh reduces many objects to one draw call.
Fill RateThe number of pixels the GPU can render per second. Transparent objects, MSAA, and high-resolution rendering all consume fill rate. Mobile GPUs have 5-20× less fill rate than desktop GPUs.
VRAMVideo RAM — dedicated memory on the GPU for textures, meshes, and render targets. Desktop GPUs: 4-24 GB. Mobile: shared with system RAM, typically 2-6 GB total. Running out of VRAM causes stuttering as data is swapped.
Fragment ShaderA small program that runs on the GPU for every pixel of every visible triangle. It computes the final color by sampling textures, calculating lighting, and applying effects. More complex shaders = slower rendering.
Vertex ShaderA GPU program that transforms each vertex (corner of a triangle) from 3D space to screen space. Skeletal animation and mesh deformation happen here. More vertices = more work.
Cascaded Shadow MapsA technique for directional lights (sun/moon) where the scene is split into distance-based layers. Near objects get high-resolution shadows, far objects get lower resolution. Each cascade is a separate render pass.
PBR MaterialPhysically Based Rendering — a material system that simulates real-world light interaction using multiple texture maps (albedo, normal, roughness, metallic, AO). More realistic but requires more texture lookups per pixel.
LOD (Level of Detail)A technique where distant objects use simpler meshes with fewer triangles. A dragon at 500 meters doesn't need 50,000 triangles — a 500-triangle silhouette suffices. Godot supports automatic LOD generation.
OverdrawWhen multiple transparent objects overlap, the GPU must render the same pixel multiple times (back to front). Particles, grass, and transparent effects are the main culprits. Mobile GPUs are especially sensitive to overdraw.
Compute ShaderA GPU program that runs general computations (not just rendering). Used by GPU particles, SSAO, and volumetric fog. Not available in gl_compatibility mode.
